- Added an optional per-user LRU memory snapshot cache behind `AML_MEMORY_CACHE_USERS`; default remains 0/off. Every successful Add increments a transactional per-user generation, so other store instances reject stale cached snapshots. Concurrent misses for one user use one loader and share its read-only result. In a fixed adjacent 10k lexical A/B, cache-off versus a one-user cache changed 96-Search wall time from 26.96 to 8.92 seconds, throughput from 3.56 to 10.76 requests/second, p95 from 10.04 to 4.15 seconds, and p99 from 11.58 to 5.31 seconds; both were 96/96 Top-1 with zero errors. The cache retains decoded text/vectors in process memory, so it remains opt-in until deployment RSS is measured.
- The load harness now records current process RSS after store initialization, Add, and Search on Windows and Linux. In a garbage-collected 10k lexical one-worker/one-Search isolation run, RSS rose 4.64 MB with cache off and 17.53 MB with a one-user cache, an adjacent-process difference of about 12.89 MB. At 1k with the real BGE backend, the corresponding increases were 3.94 and 5.19 MB, about 1.25 MB apart, while the model/runtime already occupied roughly 195-280 MB. These are process-level snapshots affected by allocator behavior, not exact cache object sizes. Under the 32-worker 10k run, coalescing also avoided large duplicate decode allocations: post-Search RSS was 75.39 MB with cache versus 224.46 MB without it. Keep the cache opt-in; measure container limits and larger real-vector corpora before changing the default.
- The Linux Docker offline job now applies a 512 MiB hard memory/swap limit and a 256-process limit, verifies Docker accepted the memory cap, enables the one-user cache, mounts a named data volume, adds 251 memories with the baked BGE model, runs 16 searches across eight threads, and verifies every Top-1 result. It then removes and recreates the offline container with the same volume, replays the identical Add idempotently, retrieves the persisted evidence, and rejects an OOM-killed container. This is a repeatable deployment and restart-recovery floor for that bounded smoke workload, not a general capacity claim.
- The first constrained Linux run completed at 457.8 MiB of 512 MiB (89.41%) with 22 processes. Because that leaves little capacity margin, the documented local command uses a 1 GiB cap and the CI workload is not enlarged. CI now emits cgroup current/peak/limit/OOM counters and requires post-workload memory below 95% of the cap, turning future steady-state memory drift into a failure.
- User-count LRU alone cannot bound a single very large user's retained snapshot. `AML_MEMORY_CACHE_MAX_BYTES` now adds a positive estimated-byte budget (64 MiB by default whenever caching is enabled). Admission counts Python containers, strings, term lists and vector buffers; oversized snapshots remain searchable but are not retained, and LRU eviction continues until both user and byte limits hold. The estimate is deliberately reported by the load harness but is not presented as an exact RSS cap.
- FastEmbed's implicit batch size of 256 made a single 1000-message Add retain about 718.2 MB RSS on the local real-BGE process. `AML_EMBED_BATCH_SIZE` is now validated at startup and defaults to 64; the embedding backend forwards it explicitly. In an adjacent one-Add/1000-message A/B, post-Search RSS fell from 718.2 to 334.3 MB while Add wall time changed from 38.96 to 38.77 seconds and both runs kept correct Top-1. This is one local run, but the large memory reduction with no observed throughput loss justifies the safer default; constrained Linux Docker remains the deployment gate.
- Byte-budget admission originally prevented an oversized snapshot from entering LRU, but waiters awakened with no reusable result and then reloaded the same large user one by one. In-flight loads now carry their generation and a transient result: requests already waiting on the same generation share the decoded snapshot once, while later requests still reload because the result is not retained. Failed loaders publish no result, so waiters retry as before. A deterministic two-thread test verifies exactly two generation reads plus one corpus load, shared object identity, and empty resident cache/load state afterward.
- The official API guide rechecked on 2026-09-10 says sessions over 20 messages or 2,000 words are split at complete message/sentence boundaries; it declares no byte limit. Individually valid fields could still total roughly 100 MB under the service's compatibility maxima and amplify further during tokenization. `AML_MAX_ADD_CHARS` and `AML_MAX_SEARCH_CHARS` now default to 200,000 positive characters. Add checks before hashing, tokenization, embedding and persistence; Search checks before tokenization. The API maps only this explicit condition to HTTP 413, while unrelated backend `ValueError` remains a non-leaking 500. The limit is far above normal official chunks and is configurable if the contract changes.
- Persisted vector blobs are decoded as float32, but Add previously wrote the encoder's raw dtype bytes. A float64 backend therefore silently turned a two-dimensional vector into four corrupted float32 values; non-finite or missing output could also create an invalid or silently lexical-only row. Add now converts every vector to a finite, non-empty, one-dimensional contiguous float32 array and rejects missing vectors or inconsistent batch dimensions before opening the write transaction. Regression tests verify float64 round-trip fidelity and that invalid output leaves both memories and the request ledger empty.
- A spawn-based multi-process regression now starts eight independent Python workers against one new SQLite path and completes 16 unique Adds. A newly opened store retrieves all 16 records and observes generation 16. This covers simultaneous schema initialization, WAL writers, transactional request ledgers and restart visibility on both Windows and Linux CI; it is deliberately bounded and is not a multi-worker capacity claim.
- A deterministic SQLite trigger now aborts Add at the final generation insert, after the request ledger and memory inserts have executed. The connection context rolls all three tables back together; after removing the injected fault, the exact same request ID succeeds and produces one memory, one ledger entry and generation 1. This verifies the transaction boundary rather than relying on SQLite assumptions.
- Runtime SQLite errors now have one FastAPI exception boundary: health, Add and Search return a stable HTTP 503 JSON response, while the server logs only the exception class and never its potentially sensitive message, path or payload. Health performs a lightweight read against the memories table instead of reporting success unconditionally. Regressions inject secrets into OperationalError/DatabaseError messages and verify neither response nor logs contain them. A real invalid SQLite file also fails closed during startup and remains unmodified.
- A standalone SQLite FTS5 probe tested direct OR-term candidate filtering without changing production Search. Hard coverage was 14/15 evidence with a 97.6% mean candidate ratio; confirmation was 12/12 with 83.7%; frozen holdout was 10/12 with 67.2%, missing both adviser identity and schedule evidence in the cross-lingual case. Direct FTS filtering is therefore rejected: it loses required zero-overlap/cross-language evidence and often barely shrinks generic-query candidate sets. The saved report is `benchmarks/fts-direct-candidate-probe.json`.
- Under the fixed 960-memory mixed workload, the bounded-burst scheduler keeps 48/48 Search Top-1 with zero Add/Search errors and lowers Search p95 from the shared-semaphore baseline of 12.88 seconds to 4.89 seconds. The earlier unbounded-priority trial reached 2.89 seconds but was rejected because it could starve Add under sustained queries. This is a finite local batch, not soak or production-capacity evidence.
- The load harness previously submitted every Add future before every Search future. At sizes above the shared executor capacity this measured executor queue order rather than sustained storage-layer competition. Mixed operations are now proportionally interleaved and reports distinguish preloaded/final memory counts, operation throughput, and incorrect Top-1 examples.
- In the expanded 96-Add (1,920 messages) / 384-Search mixed run, all writes completed with zero exceptions and the saved repeat reached 384/384 Top-1 in 55.74 seconds. Add throughput was 34.45 messages/second; Search throughput was 6.89 requests/second; Add/Search p95 was 39.89/13.92 seconds. One preceding warm repeat produced 383/384 without an exception before per-miss diagnostics existed, so perfect repeatability is not established and this workload remains a regression target.
- A 48-Add / 768-Search diagnostic reproduced the fluctuation as 767/768 and captured the miss: exact `project-code-0-16` lexical evidence was displaced by a dense-first record containing `project-code-81-16`. RRF rank-only fusion ignored the lexical score gap. A narrow 0.01 fusion guard now applies only to exact compound identifier tokens containing a digit and occurring in at most four memories. It is disabled with the lexical channel. The same real-BGE workload then reached 768/768 with zero errors; one adjacent run is evidence of the diagnosed case, not a statistical guarantee.
- Reproduced and fixed ambiguous NUL-delimited memory IDs dropping another user's record. New IDs hash a JSON array; existing rows are not rewritten. Unexpected ID collisions now fail the transaction instead of silently discarding a row.
- Reproduced and fixed replay requiring a working encoder. Ledger preflight skips encoding for completed replays/conflicts; transactional claiming remains authoritative for concurrent writers.
- Reproduced and fixed connection leakage on PRAGMA failure.
- Only RequestConflictError maps to HTTP 409; unrelated backend ValueError remains an internal error without exposing its message to the client.
- Legacy requests without a payload ledger cannot be verified from contextual display text. Reuse returns an explicit conflict and rolls back the ledger claim, without changing old memories. Callers must use a new request ID if they intentionally want a new write.
- Reproduced and fixed `know` matching `now`: English temporal markers now require word boundaries.
- Reproduced and fixed insertion-dependent tied rankings. Lexical, dense, and fused channels use a final ID tie-break; BM25 accumulates sorted query terms to avoid hash-seed-dependent floating-point order.
- Reproduced and fixed non-finite persisted vectors poisoning fusion scores. `NaN`/`Inf` vectors are treated as a damaged, rebuildable index entry; durable text remains available through lexical retrieval with a finite response score.
- Reproduced and fixed query-embedding failures taking down Search despite a healthy lexical index. Exceptions and non-finite query vectors are logged and fall back to deterministic lexical retrieval. Add encoding failures still abort before the idempotency claim, so the same request can be retried after recovery without partial writes.

## Independent high-distractor confirmation baseline (2026-09-06)

- Added six source-identity-scored cases that are disjoint from `hard_cases.json`, each with at least 15 distractors. They cover temporal supersession, English and Chinese multi-hop retrieval, negated list distractors, cross-lingual retrieval and temporal negation.
- Frozen baseline suite SHA-256: `80fd8be2d82eea1b305ea110af4472b8016428a2bb1504ed521a43c7a08f674b`.
- Before any tuning on these cases, the default top-5 result was Evidence Hit@5 58.3%, complete-case@5 33.3%, MRR 0.288. Lexical-only complete-case@5 was 16.7%; dense-only was 33.3%; default top-10 complete-case coverage was 83.3%.
- The failures expose four concrete gaps: list evidence displacement, Chinese entity-chain propagation, cross-lingual embedding quality and scoped current-fact fusion. These cases are now a diagnostic development set; a separate holdout must be authored after fixes before claiming generalization.
- First diagnosed fix: the old semantic group incorrectly treated dislike/avoidance as equivalent to a medical allergy, letting negated preference distractors dominate. Splitting medical allergy into its own concept group raised confirmation Hit@5 from 58.3% to 66.7%, complete-case@5 from 33.3% to 50.0%, and MRR from 0.288 to 0.304. All 55 tests plus hard and extended fail-on-miss regressions passed.
- Rejected trials: a packing/suitcase synonym expansion recovered one missing list item but displaced another, leaving complete-case coverage unchanged. `paraphrase-multilingual-MiniLM-L12-v2` (about 220 MB) also left confirmation Hit@5 and complete-case@5 unchanged while slightly lowering MRR. Neither change was retained; the latter also emits a FastEmbed pooling-compatibility warning that would require an explicit version/identity decision.
- Chinese-chain root cause and fix: persisted content includes a role prefix such as `user: `, while the first Chinese entity patterns assumed raw sentence starts. The linker also recomputed hop two from base lexical scores, discarding hop-one evidence. Conservative person/courier patterns now accept the real prefix and a CJK-only second hop accumulates the first ranking with a ten-seed bound. - Event-consistency root cause and fix: rank fusion treated an action plan, explicit negation, another person's action and a completed first-person action as equally valid semantic neighbors. A narrow auditable layer now activates only for positive packing/confirmation queries, boosts explicit completion evidence, penalizes explicit non-occurrence or another first-person subject, and disables itself for negative queries. The four packed items moved to ranks `[1, 3, 2, 4]`; confirmation Hit@5 rose from 83.3% to 91.7%, complete-case@5 from 66.7% to 83.3%, and MRR from 0.342 to 0.383.
- Review follow-up: first-person filtering now distinguishes “what did I pack?” from “what did my manager pack?”, so relationship-owned actions are not misclassified as another person's distraction. The missing signal was an auditable lexical bridge between booking/accommodation concepts. These six diagnostic cases have now influenced tuning and are not a holdout; the next evaluation artifact must be newly authored before claiming generalization.
