## 对实现有直接影响的信息

- 文本套件包含 PersonaMem、LoCoMo-Refined、CLBench、BEAM、LongMemEval、ScriptMem 等。
- Full 任务最长 72 小时；Search 的 `top_k` 为 100。
- Add 默认全局 64 并发、每个数据集最多 48 条记录、每块 20 条消息。
- Search 默认 32 并发，有重试和失败记录重新排队。
- 下游答题模型固定使用 `gpt-4o-mini`、温度为 0；参赛系统只负责返回记忆证据。
- 公开能力维度包括显式召回、多跳组合、时序事件、记忆治理、个性化、规则流程和隐私安全。
- 2026 首期已经结束；公开仓库说明第二期预计 2026-09-20 开放。

## 因此采用的工程决策

- 返回内容显式携带 UTC 时间与消息角色，帮助下游模型判断冲突和对话归属。
- 同时接受 Bearer、Token 和 X-Api-Key，降低 Smoke 因鉴权方案不匹配而失败的风险。
- `role` 不硬编码为 user/assistant，兼容带 system 指令的公开数据集。
- 本地测试按 64 Add / 32 Search 并发量级覆盖。
- 在公开数据集分布上验证英文、多跳、列表、时序和规则类检索，不再只用少量中文直接事实题调参。

## 2026-09-03 本机性能基线

- 48 个并发 Add、每个 20 条消息：总耗时 38.50 秒，单请求 p95 36.89 秒。
- 96 个 Search、32 工作者：总耗时 5.29 秒，单请求 p95 1.86 秒。
- 96 个精确项目代号查询全部 Top-1 命中。
- 19 条本地多类别证据基准：Hit@1 84.2%，Hit@3/Hit@5 100%，MRR 0.912。

本地证据基准包含多跳题和列表题，同一道题的多个必要证据不可能同时占据
Top-1；因此 Hit@3、Hit@5 和 MRR 比单独的 Evidence Hit@1 更能反映多证据
覆盖情况。这些样例是自建回归集，不是官方题目或官方成绩。

该结果只代表当前电脑上的合成负载测试，不等同于云服务器或官方 Full 表现；
它用于证明当前真实向量模型路径明显低于公开的 1,200 秒 HTTP 超时。

## 2026-09-06 词法容量基线

- 新增可配置、可输出 JSON 的负载工具，并以 `--no-embeddings` 隔离 SQLite、全表词法评分和 Python 并发开销。
- 使用 nearest-rank 百分位口径复跑：10,000 条记忆由 500 个 Add 请求写入，总耗时 6.90 秒，约 1,450 条/秒，0 错误。
- 96 个 Search / 32 工作者 / `top_k=100`：p50 13.43 秒、p95 15.90 秒、p99 17.67 秒、吞吐 2.26 请求/秒，0 错误，精确代号 Top-1 为 96/96。

- 零召回变化的非中文实体关联快路径会先检查少量高分种子；没有可传播专名时跳过全语料实体正则。中文仍保留从前 10 名发现第二跳实体的完整路径。相同 10k 配置下 Search p95 从 15.90 秒降至 11.32 秒，总耗时从 42.40 秒降至 28.80 秒，吞吐从 2.26 升至 3.33 请求/秒，Top-1 仍为 96/96。该结果仍不足以替代倒排候选索引。

- 在同一热缓存和代码状态下相邻 A/B，共享 ONNX 模型的嵌入并发从 1 提升到 2 后，同一 960/96 配置的 Add 总耗时从 36.74 秒降至 19.11 秒、吞吐从 26.13 升至 50.23 条/秒；Search p95 从 2.45 秒降至 1.58 秒、吞吐从 16.71 升至 22.36 请求/秒。两组均 0 错误且 Top-1 为 96/96；另以 16 工作者并发编码同一文本 32 次，向量最大差异为 0、范数均为 1。默认值设为 2，更高并发仍需单独测量 CPU/内存后配置。较早冷启动运行明显更慢，因此不使用其绝对耗时计算提升。
- 继续消融并发 4/8：Add 吞吐分别为 91.09/148.47 条每秒，但 Search p95 分别为 1.63/1.75 秒，均高于并发 2 的 1.58 秒。全部运行 0 错误且 Top-1 为 96/96。由于测试分开执行 Add 与 Search，且正式部署 CPU 配额尚未知，默认保持 2；4/8 只作为资源明确后的可选调优值，不根据单项 Add 峰值改默认配置。
- 新增有限批次混合负载：预写 960 条后，同时运行 24 个 Add（480 条）与 48 个既有记忆 Search。普通信号量下混合 Search p95 为 12.88 秒；绝对查询优先曾降至 2.89 秒，但存在持续查询令 Add 饥饿的理论风险。当前公平调度器连续放行 8 个等待查询后强制让一个等待 Add 取得槽位，并有确定性并发回归覆盖；复跑 Search p95 为 4.89 秒，较普通信号量下降约 62.0%，Add p95 为 12.19 秒，总耗时 12.97 秒。三组 Top-1 均为 48/48 且 Add/Search 都是 0 错误。它证明这个有限批次下的延迟与前进性折中；持续混合 soak 仍未验证。
- 修复负载工具先提交全部 Add、在任务数超过共享线程池容量时延后启动 Search 的测量偏差；现在按比例交错提交，并在报告中记录预载/最终数量、吞吐与失败样本。扩大到 96 Add（1,920 条新消息）和 384 Search 后，保存的热缓存运行在 55.74 秒内全部完成，Add/Search 吞吐分别为 34.45 条/秒和 6.89 请求/秒，p95 分别为 39.89 秒和 13.92 秒，Top-1 为 384/384 且零异常。此前一次同配置热运行出现 383/384，因此这不是稳定满分或生产容量证明；新失败样本字段用于下次波动时保留诊断证据。
- 将诊断扩大到 48 Add / 768 Search 后复现 767/768：查询中的低频精确编号 `project-code-0-16` 被密集第一、通用词词法靠前的 `project-code-81-16` 反超。新增保护只针对最多出现 4 次且含数字的复合标识符，并严格依赖已启用的词法通道；普通词、中文片段和 dense-only 消融不受影响。同配置真实 BGE 复跑为 768/768、零异常，Search p95 12.40 秒；单次修复后运行不足以声称长期稳定满分。
- 部署配置复查发现 `AML_MAX_CONTEXT_CHARS` 原先在每次 Add 中直接转为整数，非法值会把请求推迟到运行时才失败，零或负数还会静默改变上下文行为。现在服务在存储初始化时只解析一次并要求正整数；这属于配置失败前移，不改变合法配置下的检索结果。
- 独立 SQLite FTS5 探针验证了“直接按查询/扩展/选项词过滤候选”并不安全：hard 只覆盖 14/15 证据且平均保留 97.6% 候选，confirmation 覆盖 12/12 但仍保留 83.7%，冻结 holdout 仅覆盖 10/12、漏掉跨语种 adviser 身份与时间证据。该方案既不能稳定缩表又会切断零词面重叠证据，因此未接入正式 Search；后续索引必须保留完整密集通道和实体/跨语种桥接。
- 新增默认关闭的按用户 LRU 解码快照缓存，通过成功 Add 同事务递增的用户版本号支持跨连接/多实例失效，并合并同一用户的并发冷加载。10k 纯词法相邻 A/B 中，缓存关闭/缓存 1 用户的 96 Search 总耗时为 26.96/8.92 秒、吞吐 3.56/10.76 请求每秒、p95 10.04/4.15 秒、p99 11.58/5.31 秒，两者均 Top-1 96/96 且零错误。缓存会常驻一份解码后的文本与向量，未测部署 RSS 前不改变默认值。
- 负载工具现在同时记录 Windows/Linux 当前进程 RSS。经垃圾回收的 10k 纯词法、单 Search 隔离对照中，缓存关闭/开启后 RSS 相对 Add 后分别增加 4.64/17.53 MB，相邻进程差约 12.89 MB；1k 真实 BGE 对照为 3.94/5.19 MB，差约 1.25 MB，但模型与运行时本身已占约 195-280 MB。32 工作线程的 10k 运行中，合并冷加载使 Search 后 RSS 为 75.39 MB，关闭缓存时为 224.46 MB。这些是受 Python 分配器影响的进程快照，不是缓存对象的精确字节数；在容器限额和更大真实向量语料测量前仍保持默认关闭。
- 旧 Linux Docker 重启恢复证据曾因路径错位被撤回：CI 把卷挂载到 `/app/data`，但数据库实际位于 `/data/memory.db`；重建后先幂等重放 Add 又掩盖了数据丢失。修复后的 CI 改为挂载 `/data`，并要求重放前先检索到旧证据，重放后严格保持 251 条 memories 和 1 条 add_requests。提交 `ae522910566df159969b8fbe92f73b18035c3df5` 的精确 SHA Actions 运行 34924021883 已通过该修复后的断网恢复门禁；这只重新建立有界 Smoke 的恢复证据，不是任意语料或并发的容量承诺。
- 首次受限 Linux 运行结束时为 457.8/512 MiB（89.41%）和 22 进程，余量不足以支持盲目扩大负载。文档启动示例因此改为 1 GiB 上限；CI 输出 cgroup 当前/峰值/上限/OOM 计数，并要求负载后稳态占用低于上限 95%。
- 仅按用户数的 LRU 无法防止单个超大用户快照占满内存。新增 `AML_MEMORY_CACHE_MAX_BYTES` 正整数预算，默认 64 MiB；估算包含 Python 容器、字符串、词项列表和向量缓冲区。超预算快照仍可检索但不常驻，多用户时会按 LRU 淘汰直到同时满足用户数与字节预算。该估算不替代容器 RSS 硬限。
- FastEmbed 隐式批大小 256 在单次 1000 条 Add 的本地真实 BGE 进程中，Search 后 RSS 约 718.2 MB。新增启动时校验的 `AML_EMBED_BATCH_SIZE`，默认 64 并显式传入 FastEmbed。相邻 A/B 中 RSS 降至 334.3 MB，Add 耗时从 38.96 秒变为 38.77 秒，两次 Top-1 都正确。这仍是单次本地证据，最终部署以受限 Linux Docker 为准。
- 字节预算会阻止超大快照常驻，但初版在并发等待者醒来后无法复用该结果，会依次重读和解码同一大用户。在途加载现保留 generation 和临时结果：已等待的同版本请求共享一次加载，结果仍不进入 LRU；加载失败时不发布结果，等待者继续重试。
- 2026-09-10 重新核对官方 API 页：超过 20 条消息或 2,000 个词的会话会在完整消息/句子边界分块，未声明字节硬上限。为防止形式合法的超大列表在分词和嵌入时放大内存，`AML_MAX_ADD_CHARS` 与 `AML_MAX_SEARCH_CHARS` 默认均为 200,000 正字符，超限在重计算前返回 HTTP 413。该值远高于官方正常分块，且可通过环境变量调整。
- 向量持久化格式固定为 float32；启用嵌入时，Add 现在会先把每条编码器输出归一化为有限、非空、一维、连续的 float32 向量，并在向量缺失或同批维度不一致时整批失败。这样避免 float64 原始字节被按 float32 错读、静默生成纯词法行，也避免无效向量和 request ledger 部分写入。
- 新增有界多进程恢复测试：8 个独立 spawn 进程向同一新 SQLite 文件完成 16 次 Add，重开 store 后 16 条均可检索且 generation 为 16。它验证该规模下的并发初始化、事务台账与重启可见性，不代表多 worker 容量上限。
- 新增事务故障注入测试：在 generation 写入处用 SQLite trigger 强制中止，验证此前执行的 request ledger 和 memory 插入会一起回滚；移除故障后，相同 request_id 可成功重试，最终三项状态严格一致。
- 运行期 SQLite 异常现在由统一 API 边界转换为不含内部细节的 HTTP 503 JSON，服务端只记录异常类名，不记录可能包含路径或请求正文的异常消息。`/health` 不再无条件报健康，而会轻量读取 memories 表。测试覆盖 health/Add 的 OperationalError、Search 的 DatabaseError，以及真实损坏数据库在启动时保持原文件并明确失败。
