# Full 前提分审计

最后核对：2026-09-22（Asia/Shanghai）。本文件记录官方 Smoke 通过后的离线提分判断。
它不包含官方隐藏样本、请求正文、答案或密钥，也不把合成基准等同于 Full 成绩。

## 失分假设与本地证据

当前线上配置关闭 embedding，因此先用与线上一致的纯词法模式重跑现有公开/合成套件。

| 套件 | Hit@1 | Hit@5 | MRR | Complete@5 | 主要薄弱点 |
| --- | ---: | ---: | ---: | ---: | --- |
| core | 0.84 | 1.00 | 0.91 | 1.00 | 名单证据排序 |
| extended | 0.75 | 0.94 | 0.83 | 0.92 | 跨语言 |
| hard | 0.33 | 1.00 | 0.60 | 1.00 | 多跳和名单排序 |
| confirmation | 0.17 | 0.83 | 0.40 | 0.67 | 多跳、时间否定/覆盖 |
| holdout | 0.17 | 0.75 | 0.36 | 0.67 | 跨语言、多跳、时间覆盖 |
| blind2 | 0.36 | 0.91 | 0.60 | 0.83 | 时间覆盖、名单完整性 |
| blind3 | 0.55 | 1.00 | 0.71 | 1.00 | 排序而非漏召回 |

这些集合已经参与过历史诊断，不能继续充当真正盲测。它们只能帮助形成假设；任何新算法
必须先冻结新的独立高干扰套件，再首次运行。

逐案例检查表明，主要失败不是 API、持久化或并发错误，而是检索结构问题：

1. 查询需要两到三段关系链时，单段表面词匹配的干扰项可能占据前列；相关链条虽常在
   Top-10/Top-100 内，但顺序和完整性不足。
2. 当前/历史/取消/否定语义只有窄范围规则；缺少明确 `current` 等词时，系统无法稳定
   判断是否应优先最新事实。
3. 中英文零词面重叠仍依赖小型可审计词典或英文 BGE 的有限跨语言能力。
4. 名单问题容易被“同一活动但未确认、已撤回、他人事件”等高相似干扰项挤占。
5. 相邻对话上下文会提高证据可读性，但也会制造重复文本；Top-100 下需要关注传给回答
   模型的有效证据覆盖率，而不只看单条 Hit@1。

## 多语言模型消融结论

试验候选：`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，FastEmbed 公布
ONNX 体积约 0.22 GB；当前 `BAAI/bge-small-en-v1.5` 约 0.067 GB。

- 默认 1.5:0.5 词法/密集权重下，候选在 blind3 改善跨语言排序，但 confirmation 的
  Hit@5 从当前英文 BGE 的 1.00 降至 0.917，holdout 完整覆盖没有改善。
- 0.5:1.5、1:1 和 0.25:2 三组消融均出现套件间明显回退，没有形成独立集合上的一致优势。
- FastEmbed 0.8.0 对该模型发出 pooling 行为迁移警告；若不额外固定自定义模型定义，
  同名模型在版本变化后可能产生不同向量。
- 更大的模型会压缩 Railway 免费规格的内存余量；现有 10k BGE 测量已经表明语料增长时
  峰值内存不能忽略。

结论：**不采用该多语言模型，不修改 Docker 或线上 embedding 配置。** 下载和消融只在
本地缓存中发生，没有写入仓库、数据库或部署。

## GitHub 工程对照

| 项目 | 可借鉴思想 | 不直接采用的原因 |
| --- | --- | --- |
| [xMemory](https://github.com/HU-xiaobai/xMemory) | 分层检索、降低重复、聚合完整证据 | 依赖大模型/GPU，工程形态不适合当前部署 |
| [Graphiti](https://github.com/getzep/graphiti) | 来源保留、事实有效期、关键词+语义+图遍历 | 依赖 LLM 和外部图后端，超出零预算范围 |
| [Mem0](https://github.com/mem0ai/mem0) | 实体链接、多信号融合、时间感知 | README 明示部分基准来自托管专有优化，不能照搬分数 |
| [HippoRAG](https://github.com/OSU-NLP-Group/HippoRAG) | 关联式多跳检索和图扩散 | 完整实现需要 OpenIE/LLM/GPU，部署成本过高 |

四者共同支持“关系、时间、多信号和多样性”方向，但不能据此声称本项目复现了论文方法
或能取得其公开分数。后续只实现能在 SQLite/CPU 内明确消融的小组件，并保留原始证据。

## 已确认的改动方向与门禁

优先级按以下顺序执行：

1. **P0：建立新的冻结盲测。** 覆盖未参与当前规则开发的跨语言、两/三跳、时间覆盖、
   否定名单和高重复上下文；先提交案例与 SHA，再首次运行。
2. **P0：关系链覆盖重排。** 在现有 BM25 候选上做有界的一至两跳实体/稀有主题传播，
   目标是把链条证据成组带入前列；不得引入无限图遍历或跨用户状态。
3. **P0：时间与否定一致性。** 用明确、可消融的查询意图和事实状态信号区分当前、历史、
   已取消和未确认，不删除原始记忆，不把推断写成事实。
4. **P1：结果覆盖与去冗余。** 在不丢失来源的前提下减少高度重叠的上下文片段，测量
   Top-100 的唯一证据覆盖、字符预算和排序回退。
5. **P1：容量门禁。** 每个候选运行完整测试、冻结盲测、10k 负载和受限 Docker；任何
   质量提升若以明显超时或内存风险为代价即拒绝。
6. **P1：新版本与 Smoke。** 只有新盲测和既有回归同时提升，才生成新 SHA/版本，完成
   版本一致性核对后使用一次新 Smoke。建议总共只预留 3--5 次有证据的 Smoke 迭代。

当前不应做的事：扩大人工同义词表去追逐已见案例、反复修改融合权重、导入完整图系统、
直接开启更大向量模型、对同一 Smoke 结果反复试分，或在旧版本名下静默替换线上代码。
